# Changelog

## Unreleased

- Made a long verification say what it is doing, and stopped a failed one forgetting where it got to. A caller polling a running profile saw `state: running` and a progress message that carried only an elapsed counter, because the two long gates are declared as a single command: `progress_current/total` was always `0/1` and the eight stages the script prints never reached the operation. `scripts/verify-change.sh` now runs one stage per invocation (`--stage typecheck`), so the reviewed profile can declare typed steps against the same script rather than redefining the stages -- `make verify` and the profile cannot drift into meaning different things, and the profile's executable surface stays at one script. Separately, a failed, cancelled or orphaned operation now KEEPS its last progress message. Clearing it was an explicit invariant (`terminal_message_mismatch`), reversed deliberately here: the reason to clear was that a "running ..." string on a finished record could be misread as liveness, but `state` and `phase` both say otherwise, and the rule cost the reader how far the work got on exactly the records where that is the first question -- a 30-minute profile that timed out recorded only that it failed.

- Fixed a cancel that a heartbeat could defeat. `request_cancel` reads the operation, decides, then saves with a compare-and-set against what it read -- and a running worker's heartbeat moves `updated_at` without changing anything that decision consumes, so a cancel could fail `OPERATION_STALE` for no semantic reason. Surfaced in CI on timestamps 60 milliseconds apart against a 0.5s heartbeat interval, on one runner out of five, which is also why it had gone unnoticed: it is rare, typed and retryable, so in production it looks like a blip rather than a defect. The caller in that path passed no `expected_updated_at` -- it asserted nothing and was still told its assertion failed. The read-modify-write now re-reads and recomputes, bounded to three attempts, and `request_operation_cancellation` being pure means a retry re-evaluates terminality and cannot cancel something that finished in between. A caller that does pin `expected_updated_at` still gets the conflict, because that assertion is theirs and it genuinely failed.

- Fixed the pull-request coverage-map check demanding what cannot be delivered, and stopped the live-activation drill destroying the reason it failed. Only executed *function-body* lines carry a per-test coverage context, so a `ports/` Protocol (`...` bodies), a generated constants module (no functions) and a package `__init__.py` (a lazy `__getattr__` production never reaches) can never appear in the map however many tests import them. The check rejected them anyway and told the author to run `make test-map`, which fixes nothing: on the identity branch 15 of the 16 modules it rejected were exactly these. It now judges mappability first and reports the unmappable ones as information rather than failure -- the empirical basis being that zero of the 343 mapped files are `__init__.py`. Separately, `live-activation-sandbox.sh` ran `rf setup --approve` under `>/dev/null`, so a red gate said `rf setup --approve failed` and nothing else; it now keeps the output, which immediately named the real cause on the identity branch (`COMMIT_IDENTITY_UNRESOLVED`).

- Added the pull-request half of the coverage-map gate. Rebuilding the map needs a full recording run, so the authoritative check is push-only -- by which point the stale entry is already on `main`. `select_affected_tests.py --check-map-freshness` is static instead: it reads the diff and the map, runs no tests, answers in under a second, and fails when a changed package module is absent from the map. That is the common case and the one that accumulated 170 files. The remedy is `make test-map`, which is a full run and therefore local; the trade is deliberate, since paying a recording run inside every pull request would cost more than the escalations it prevents.

- Put a gate on the coverage map, which decides how narrow a pull-request test run may be and had nothing watching it. It went eight days without a rebuild, accumulated 170 unmapped source files, and quietly sent five of the last eight commits to the whole suite -- the behaviour it exists to avoid. `make test-map-check` records a fresh run and reports drift instead of writing, and the push job in `production-gate.yml` runs it. The comparison is deliberately asymmetric: a source file the fresh run covers but the committed map omits is a failure, because the selector fails closed on an unmapped module; the reverse is only reported, because source can branch on platform and a map recorded on another OS legitimately covers files a given runner never executes -- failing on that would make the gate depend on who regenerated it. A committed entry naming a test file that no longer exists is also a failure. Recording needs a full run, so the job is push-only and the aggregator names both `success` and `skipped` explicitly rather than accepting whatever it finds.

- Regenerated `tests/coverage-map.json`, which had not been rebuilt since it was introduced on 2026-07-21 and had gone stale enough to defeat its own purpose. 170 of 439 source files were absent from it, and a changed source file with no mapping fails closed to the full suite by design -- so five of the last eight commits ran everything, which is the behaviour the map exists to avoid. It now maps 327 source files to 170 test files, and the same eight commits fall back three times instead of five. The remaining three come from two files that no test *executes* even though tests do assert on them: a generated constants module and a `Protocol` definition, neither of which has function-body lines for coverage to attribute. Refresh with `make test-map` after material source or test changes.

- Replaced the partitioned test-shard runner with the two lanes the suite is actually fast in, and split the change gate from the release gate. `scripts/run_test_shards.py` ran the suite as four independent pytest processes balanced from a recorded-duration cache; measured against the same tests under xdist that was several times slower, because these tests are dominated by git subprocess spawns and four concurrent processes oversubscribe a machine whose measured stable worker cap is three. One file recorded at 322.8s inside that runner took 33s alone under identical coverage flags, and the cache made it self-perpetuating: durations were persisted only when a run completed, so a run killed by the profile timeout left the next one balancing by file size again. It is now `scripts/run_test_suite.py`, running the serial lane (the `parallel = false` groups) and then everything else in one xdist run at `REPOFORGE_TEST_WORKERS` (default 3). New `scripts/verify-change.sh` and `make verify` carry everything a change can break -- contracts, corpora and control-plane fault gates, lint, strict types, the whole suite -- and leave the branch-coverage floor, the builds and the installed-wheel smoke to `scripts/verify-production.sh` and to CI, which already runs them on every push. `make check` is unchanged and remains the authority.

- Made a tunnel restart leave a durable trace. `restart_count` is a gauge the restart policy consumes and resets after `stable_health_reset_seconds` of calm, so sixty seconds after the last restart the record reads `0`. On 2026-07-28 the connector was torn down twice in twelve minutes by the tunnel's own MCP connection TTL, and the record afterwards published `phase: healthy, restart_count: 0, consecutive_health_failures: 0` -- every durable fact insisting nothing had happened, while the only evidence left was the raw tunnel log. `restarts_total` and `last_restart_at` are evidence rather than policy: nothing resets them, and they are seeded from the previous record so a supervisor that itself restarted does not republish a clean slate.

- Fixed the two places that still pinned pytest's timeout to 60s, below the app's own 120s git subprocess budget. 546cf52 removed that inversion from `pyproject.toml` -- where the comment explaining it still sits -- but `scripts/run_test_shards.py` and the push job in `production-gate.yml` carried their own `--timeout=60`, so the authoritative gate and CI both ran at the ceiling that was measured to kill healthy-but-slow git calls under contention. Each false timeout also costs a full 60 seconds of wall clock before the run gives up. Both now inherit the repository setting, and the test that pinned the old value asserts the runner declares no timeout of its own.

- Fixed risk path globs matching far more than they name, which sent most of a workstream to the slowest verification profile. Matching went through `fnmatch`, where `*` crosses `/`, so `**/runtime*.py` -- written to name a module -- also matched every file under any `runtime/` directory, and `**/auth*.py`, `**/schema*.py` and `**/security*.py` had the same reach. Five of the last eight commits on this repository were escalated to the final profile by that over-match alone; three of them were runtime-package members no filename pattern had selected. Segments now match segment-by-segment: `*` and `?` stay inside one path component, a whole `**` component spans zero or more directories so `**/uv.lock` still matches the manifest at the root, and a trailing `/**` still covers an entire subtree. This changes only risk scoring and verification depth. The path matchers that enforce the safety boundary -- denied paths, policy, command sources -- are deliberately untouched, since narrowing a deny rule would weaken it.

- Made an expensive verification profile impossible for a model to spam. Admission now JOINS identical durable work already in flight instead of admitting a duplicate -- two runs of the same profile against the same exact snapshot cannot reach different answers, and they would only contend for the same workspace lock -- so the caller gets back the operation actually producing the answer. Reviewed configuration gained two per-profile fields: `model_invocable = false` reserves a profile for the operator and CI while leaving it available to both, and `min_interval_seconds` puts a floor under `force_rerun`, which exists for external changes that do not touch the tree and is also what turns a 30-minute gate into something repeatable at will. Both refusals are typed (`PROFILE_NOT_MODEL_INVOCABLE`, `PROFILE_RERUN_TOO_SOON`) and enforced on the model-facing side of the durable boundary, where the caller's origin is still known -- the worker that executes the profile later runs as `background_worker` and could not have judged it. Defaults keep every existing configuration unchanged.

- Fixed a single misbehaving control-plane client being able to disable the runtime control plane permanently. The Unix control server served one connection at a time with no read deadline, and `accept()` returns a blocking socket regardless of the listener's timeout -- so a client that connected and stayed silent held the accept loop forever, and when it disconnected, `sendall` to the closed peer raised outside the guarded block and killed the serve thread outright. The process kept running and its watchdog kept recording `phase: healthy` while every read that needed the control socket timed out, and both recovery commands (`rf runtime restart`, `rf runtime stop`) were themselves routed through the dead control plane, so recovery required signalling the supervisor by hand. Each exchange is now bounded in time and in bytes, and nothing a peer does can end the accept loop: a dropped connection costs that one exchange. Runtime health also stopped taking the control plane on faith: `control_plane` is now an observed health check, so a runtime that cannot answer control requests reports itself degraded instead of publishing `healthy` from the watchdog loop that outlived the one serving them -- which is what made the incident read as a state fault rather than a dead control plane.

- Fixed activation evidence reporting `agreement=diverged` on a healthy, converged installation. The verdict compared the receipt's recorded process identity and tool-surface hash against the live ones, but both describe a single process instance and a single release: a watchdog restart changes the first and a later release activation changes the second, so it called a correct activation a failed one -- observed on a live installation, where it also cost diagnosis time while triaging an unrelated fault. `agreement` now compares the configuration generation the runtime serves, which is what the activation decided and the only recorded fact that survives a restart; `unverifiable` still covers a receipt that recorded no generation. The two changes are reported as facts instead, through the additive `process_restarted_since_activation` and `tool_surface_changed_since_activation`, each `null` when either side is unknown rather than defaulting to "unchanged". Adding those output fields changes the tool-surface hash, so the connector must rediscover after activating this.

- Fixed the managed MCP runtime serving without knowing which configuration generation it serves, which made every durable verification admitted through the connector unrunnable. The per-generation service container was built from a generation it already knew but never passed to `build_application`, so the request side ran at the default 0 while the execution worker ran the real generation; the worker claims only matching work, so the item was never claimable and recovery terminalized it as `OPERATION_GENERATION_STALE` about 30 seconds later. Broken since the generation gate landed, and invisible to the test corpus because tests build BOTH sides at generation 0 -- the new coverage asserts the production topology instead, with request and worker sides composed independently against the real generation. That composition also moved out of a closure into `build_generation_service_container` so it is directly testable. Recovery's staleness rule now fails only work from an OLDER generation: the symmetric comparison also failed work from a newer one, which is the normal state for a few seconds during a hot reload and destroyed valid work while reporting the operator's own config change as an error.

- Fixed an activation that raced its own supervisor handoff, could not unwind, and then blocked every later activation with no forward path. The incoming supervisor took `runtime-single-instance` with no wait while the outgoing one still held it, so it died on `LOCK_TIMEOUT` and a healthy activation was reported as a failure; it now waits a bounded interval and reports a typed `RUNTIME_SUPERVISOR_HANDOFF_TIMEOUT` naming the holder, and an activation drains the incumbent by identity before kickstarting the OS-managed job, because `kickstart -k` only replaces the process launchd itself owns. A failed activation whose unwind also fails is no longer reported as a rollback: `ACTIVATION_FAILED_ROLLBACK_FAILED` states what `current` points at and what to do next, and `rf upgrade` exits non-zero when a `--watch` window ended in a rollback. New `rf upgrade reconcile` (`make reconcile`) terminalizes an activation whose target the live runtime is observed serving and health-verified -- the state where re-running was refused while the only other advice would have demoted a healthy runtime -- and the activation guard reconciles that case automatically instead of deadlocking. `rf version status` now names the same next action, adding `incomplete_activation_reconcilable`, and the live-activation gate samples the single-instance lock across a real handoff so two live supervisors fail the gate.

- Added `strategy` to `workspace_refresh` conflict resolutions, so keeping one side of a conflict no longer requires echoing the whole file back. `content` is unchanged and stays the default; `ours` and `theirs` read the side to keep from the commits the plan is already bound to, deliberately not from the preview's conflict evidence, which is clipped to a byte budget and would otherwise write a silently truncated file. A resolution carrying both a strategy and a body is refused rather than resolved by guesswork. The tool surface stays at 28.

- Added an upgrade-compatibility gate that boots against a populated state root, and fixed the four durable stores it caught. Every other test starts from an empty state root, so a record written by a previous release never existed in CI -- which is how a release that could not start at all passed ten green checks. The new gate seeds each store swept at startup with a record this release cannot decode and asserts the runtime still starts, and it carries a negative case that reintroduces the defect so the gate cannot pass by testing nothing. `operations`, `operation-work-v1`, `effect-receipts` and `runtime-activations` all failed it: their scans raised instead of reporting. Sweeps now skip records they cannot decode and report them (`unreadable_record_ids`, `unreadable_operation_ids`), while a direct `read()` of one exact record stays strict.

- Fixed an upgrade that could not start on any installation with existing PR check watches. Raising `PR_CHECK_WATCH_SCHEMA_VERSION` to 2 added two required fields, and every already-stored v1 record then failed to decode; because `list_records` raised on the first one and startup calls it through `resume_active()` -> `build_application()`, no process could start at all -- MCP, the execution worker, or a plain `rf doctor`, which reported `PR_CHECK_WATCH_STATE_CORRUPT`. A scan now skips records it cannot decode and reports them in `PrCheckWatchPage.unreadable_operation_ids`, while a direct `read()` of one exact watch stays strict. Resume records the watches it passed over in the audit trail, since a skipped watch is no longer polled. The v1 records are not migrated: v2's `remote_version`/`stability_version` are exact remote-state tokens, and inventing one would fabricate the exact-state binding those tokens exist to guarantee.

- Made every `workspace_verify` execution durable work instead of a request-thread command. Admission persists a schema-versioned work envelope beside the operation record, a dedicated managed-runtime worker process claims it under a compare-and-swap lease, and `background=false` only bounded-waits on that operation, so a client timeout or disconnect no longer owns or destroys execution state. A blocked ten-minute command no longer delays `operation` reads, listing, or cancellation; queued work survives a restart and runs exactly once; a claim that never spawned a child is requeued while ambiguous mutating work is orphaned with evidence rather than retried. Operations now report `attempt`, `heartbeat_at`, a read-time `heartbeat_age_seconds`, and `evidence_complete`, and a terminal operation can no longer retain `phase=running`. No tool was added: the surface stays at 28.

- Fixed `workspace_status` of a workspace with a running verification blocking for the entire command. Durable execution took the command off the request thread, but the worker still holds that workspace's lock for the whole run, so a status read of the busy workspace serialized behind it. Status reads now wait at most `server.status_read_lock_timeout_seconds` (default `0.5`) for the lock and otherwise read without it, reporting the additive `read_consistency` field as `locked` or `concurrent_write` rather than presenting an unsynchronized read as an exclusive one. A `concurrent_write` read never writes its fingerprint back to the shared cache, and its fingerprint must not be used as an exact-state binding for a mutation. The tool surface stays at 28.

- Fixed process containment reporting a successfully killed child as having survived. `killpg(pgid, 0)` also succeeds for a group whose members have already stopped and are only awaiting a `wait()` from their parent, so reaping now confirms liveness by process inspection (matching the Linux `/proc` reader, which already rejected state `Z`) and still fails closed as alive on a host it cannot inspect. Cancelling an execution owned by the current process now signals that owner's own token before any reap, so the run records the cancellation in its result and audit trail instead of reporting an ordinary command failure, and a cancellation observed between commands is stamped as cancelled too.

- Changed `workspace_diff` to return hunk-free per-file summaries by default, reducing routine review payloads while preserving exact status and line counts. Callers that need patch content must now send `include_hunks=true` with a narrow `path_glob` and small `max_files`; the 120 KB byte budget remains a safety cap rather than a target response size.

- Added complete bounded failing-selector evidence and `workspace_verify.rerun = "failed"` for enrolled diagnostics. Failed pytest node IDs are extracted before output truncation, truncated failures carry a private content-addressed full-output reference, reruns execute only the exact last failure set on the identical workspace fingerprint, and expected TDD RED failures are classified separately from unexpected failures.
- Added durable per-step background profile progress and an additive `operation.action = "wait"` long-poll mode. Step start/completion updates expose bounded liveness evidence; wait wakes on progress or terminal state, caps `timeout_seconds` at 60, returns typed timeout evidence instead of an empty poll, and publishes `suggested_poll_after_s`, progress unit/message, and ETA when computable. Acceptance coverage reaches terminal state in at most five non-empty wait calls.
- Added advisory post-mutation Tree-sitter syntax evidence to every `workspace_mutate` dry-run, no-op, apply, keyed receipt, and keyed replay response. Python, JavaScript, JSX, TypeScript, and TSX return bounded same-response diagnostics; unsupported grammars, invalid UTF-8, parser failures, observed budget overruns, and historical v1 receipts report explicit `unknown` rather than implicit success. Syntax errors never block the journaled mutation, while the response summary prominently reports `parse_ok=false`; generated contracts and a frozen-corpus p95 acceptance test cover the public shape and 100 ms/file budget.

## 2.1.0 — 2026-07-16

- Published concrete nested `workspace_edit` input items plus `context_lines` and `max_results` numeric bounds in the frozen MCP release contract, so clients can validate calls locally instead of discovering these constraints through failed tool calls.
- Replaced the checked-in production ticket graph with bounded GitHub-native traversal of sub-issues, blocked-by relationships, live issue state, and optional Project V2 metadata; graph, readiness, and issue-spec tools now share cached snapshot evidence with `fresh=true` bypass, and the legacy Project apply path is retired so GitHub remains authoritative.
- Added an opt-in loopback `rf webhook serve` ingress for signed `issues`, `sub_issues`, `issue_dependencies`, and `projects_v2_item` deliveries; it validates and deduplicates bounded payloads and invalidates only the affected repository's graph cache.
- Added agent-facing configuration administration, gated by capability delta. Three new MCP tools:
  `config_inspect` (read generations, one repository's effective policy, and pending changes),
  `runtime_logs_read` (bounded redacted audit-trail and runtime-log reads for debugging), and
  `repo_policy_apply` (set/remove command profiles, diagnostics, formatters, or known policy
  overrides through the reviewed immutable-generation pipeline, with `dry_run` previews).
  Restrictions and metadata-only changes are accepted immediately and hot reloaded in process;
  capability expansions are never applied on the model's authority — they are persisted as a
  pending change the operator approves out of band with the new `rf config pending`,
  `rf config approve CHANGE_ID`, and `rf config reject CHANGE_ID` commands, and the approval token
  never transits the model conversation. Accepted customizations are recorded as a durable
  per-repository `policy_patch` in the editable source configuration (round-tripped by
  `parse_source`/`render_source`), so custom profiles, diagnostics, and formatters now survive
  `rf repo refresh` instead of being regenerated away. Every candidate is validated with the full
  configuration loader before acceptance and fails closed; on transports without an in-process
  runtime the tools return a structured `CONFIG_ADMIN_UNAVAILABLE` error.
- Modernized the tracked example configurations: `config.repoforge.toml` and
  `config.work-frontier.toml` are now v2 *source* configs whose hand-tuned profiles,
  diagnostics, and formatters ride in `[repo.policy_patch]` tables instead of the legacy
  resolved `[server]`/`[repositories.*]` layout; `PLACEMENT.md` now routes installation
  through `rf repo refresh --accept`, and the superseded personal `config.local-dev.toml`
  was removed. Legacy resolved configs remain supported for serve/doctor/runtime only.
- Fixed a cross-repository Project-item mapping bug: `GhTicketProjectGateway` mapped GitHub Project V2 items by issue number alone whenever the item's repository identity was missing or unparseable, which could point a Project sync mutation at the wrong repository's issue in a multi-repo Project. It now fails closed (excludes the item from the snapshot) unless the repository identity is present and matches.
- Fixed a stuck-`RUNNING`/leaked-lock bug in `workspace_run_profile`'s background path: if `background_tasks.submit(...)` raised instead of returning `False`, the workspace lock was never released and the operation record was left `RUNNING` forever. The submit call is now wrapped so a raised exception unwinds identically to a rejected submission (unregister the cancel token, release the lock, fail the operation closed) before propagating.
- Added `identities_truncated`/`items_truncated` to `TicketProjectSnapshot` and a derived `snapshot_incomplete` flag on `TicketSyncPlan`: a bounded issue-identity page scan or Project item-list fetch that could not confirm it observed every record now says so, instead of the sync planner reading a missing identity/item as confirmed drift.
- Bound the GitHub read cache key to the resolved repository path in addition to `repo_id`: a `repo_id` label repointed at a different local checkout (config edit, reload, or repository migration) can no longer serve a stale cross-repository cached issue/PR payload within TTL.
- Added an intermediate size check inside `workspace_edit`'s per-file edit loop so one oversized replacement in a multi-edit batch is rejected as soon as it grows the in-memory buffer past `max_file_bytes`, rather than only after every edit in the batch has run against it.
- Replaced `workspace_replace_text` with `workspace_edit`, a breaking change to the MCP tool surface: instead of one exact-replacement call per file, `workspace_edit` accepts a `files` list where each entry carries its own `expected_sha256` and ordered `edits` (at most 20 files, at most 20 edits per file). Every file is verified and transformed in memory before anything is written, so a multi-file edit is now atomic — a mismatch on any file leaves the whole workspace untouched — closing the gap where a multi-file patch rejected by `workspace_apply_patch`'s hunk-context normalization had no atomic fallback short of one `workspace_replace_text` call per file.
- Closed the remaining contract gaps in the recent agent-effectiveness work: `repo_issue_next` now emits one outer audit event even for repository-resolution failures; the GitHub read cache is a true persistent LRU without extending TTL freshness; result-size averages use only successful payloads whose size was actually observed; background profile admission is atomic across workspaces and completed structured results are stored privately, boundedly, and resolved by `operation_status`; `repo_task_context` reads recent commits from the supplied workspace branch; and the checked-in roadmap now marks the verified closed tickets as Done.
- Added an additive `next_step` field to `workspace_pr_checks` and `workspace_read_file` carrying a
  stable default plus three bounded, advisory, session-local nudges that name a cheaper or more durable
  tool at the exact moment an inefficient pattern occurs, inside the structured field an agent already
  reads: a `workspace_pr_checks` result polled a third time within 10 minutes for the same workspace
  while still pending names `workspace_pr_watch` with a concrete example call; a `workspace_pr_checks`
  result whose summary contains a failing *required* check names `workspace_pr_check_details` and
  `workspace_pr_failure_evidence` with the exact selector for the first failing required check,
  immediately and without any repetition threshold; and a `workspace_read_file` result on the fifth
  consecutive single-file read against the same workspace within one minute names `workspace_read_files`
  batching, resetting the moment that workspace uses `workspace_read_files`. No tool, parameter, schema,
